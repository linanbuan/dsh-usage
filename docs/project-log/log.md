## 2026-10-25 · 面板「累计用量」比真实用量少约三分之二（1.5.0）

### 目标与范围

- 现象：设置页「用量」的累计用量只有十四亿多，用户认为真实用量在四十亿量级。
- 范围：查清口径是否算错 → 结论是没算错；随后按用户决定改为「只补用量记录、不恢复已删除的会话」。

### 排查得到的事实

- 面板数字与磁盘上现存会话日志**逐条一致**：把全部现存日志独立解压重算，累计、峰值单日、按天数值都与面板相同；
  每条事件的 `totalTokens` 与 `input + output + cacheRead + cacheWrite` 相等，数千条无一例外。
- 差的那部分不是算法问题，是日志本身少了：一份 10-23 的本机 `sessions` 备份里有 296 个会话，其中 **169 个在当前会话根目录已不存在**，
  对应 18 个项目目录在同一分钟内被清空，回收站无残留。备份合计减去这 169 个会话、再加上备份后新增的会话，与现存合计逐位吻合。
- 因此「累计 < 真实」的根因是**会话日志被删**，插件按现存日志统计，只能得到现存的那部分。

### 实际改动

- `lib/ledger.js`（新增）：账本本体 —— 折叠原语、`syncLedger`（按会话 revision 增量读尾）、`ledgerView`、`mergeLedgers`、原子读写与 `.bak`。
- `index.js`：`/api/usage/usage` 改由账本作答；新增 `syncIntervalMs` 定时同步（下限 60 s）、激活预热、dispose 落盘；响应里的 `scan` 说明账本口径。
- `client.js`：概览条下新增账本说明行（账本起始日、上次更新、本机现存日志与会话数、已删除会话数），中英词表与 `trf` 插值同步。
- `tools/seed-ledger.mjs`（新增）：没有 Harness 时用同一份折叠代码推进账本；`--backfill --from <备份会话根目录>` 只加不改地补记已删会话。
- `test/selfcheck.mjs`：新增 A2 节账本契约断言（只增不减、幂等、丢弃重写、合并、拼写别名、坏文档修复、路径优先级）。
- `docs/token-ledger.md`（新增）：数据模型、同步算法、调度、边界与落地记录。
- `README.md` / `README.en.md` / `cordis.patch.yml` / `package.json`（1.5.0）同步。

### 遇到的问题与原因

1. **面板打开即全量折叠 149 个会话**（2–3 秒），且删会话会让总量变小 —— 于是改成持久化账本：每条会话记住读到第几条，只读新增尾部。
2. **合并写盘的平局把新 revision 丢掉**：两个窗口共用一个 home 时，同 offset 保留磁盘旧行，导致每轮都判定「变了」，把 2 ms 的空闲同步退化成 3 秒全量扫描。改为平局取 `lastSeenAt` 更新的一行。
3. **会话 id 有两种拼写**：早期 id 是裸 UUID，后来带 `session-` 前缀，本机两种目录都在。若把前缀去掉记键，宿主首次同步会把同一批会话当新会话再记一遍，总量翻倍。
   处理：键用目录名原文；同步时把「另一种拼写」的行**就地改名收养**；写盘合并时把成对拼写**折叠成一行**（只改同步侧不够，磁盘上的旧键会在下一次合并里被补回来）。
4. **profile 的 `link:` 依赖指向了本机的旧副本目录**：重启后 Harness 按 profile 的 `package.json` 重跑安装，把手工改过的 junction 覆盖回去，加载的是旧版本，面板又回到「只剩现存日志」。
   处理：改 profile 的 `package.json`（与 `pnpm-lock.yaml` 同步）指向本仓库，再重建 junction —— 只改 junction 是派生状态，改了不算数。

### 结果与验证

- `node test/selfcheck.mjs` 全绿；端到端用真实会话目录挂载 `index.js`：账本作答、`source: ledger`、已删除会话计入累计，第二次读取为空闲路径（0 次日志读取）。
- 账本行数 = 现存会话 + 已删会话；每日聚合与备份折叠逐日一致（仅「今天」因日志仍在增长而不同）。
- `--backfill` 只加不改：重复执行不会重复计入，补记来源里仍在存的会话被跳过。

### 遗留问题与风险

- 面板要**重启 Harness** 才会读到新实现（Host 半走 ESM 缓存）；浏览器半由 HMR 自动重载。
- 本机仍留有一份 1.4.0 的安装副本目录，已无任何引用；若再次被 `link:` 指向，会重新加载旧代码。
- 若再次发生「会话日志批量消失」，账本能保住已记录的用量，但**不会**自动恢复会话文件本身（本方案不碰会话日志）。

## 2026-10-31 · 账本迁到每用户数据目录：卸载插件或重装 DSH 不再丢累计（1.6.0）

### 目标与范围

- 1.5.0 的累计记在 `$DSH_HOME/usage-ledger/ledger.json` 下，位置跟着 Harness 的 home 走：换一个 home（卸载重装后常见）
  就等于换了一份账本，旧文件还在但没人读，面板上的累计于是看起来被清空。卸载插件本身不删这份文件，但它的位置与
  DSH 的 home 绑在一起，用户无法预期它在卸载 / 重装之后还在。
- 目标：按「无论卸载插件还是卸载 DSH，用量历史都保留；下次安装接着继承」来改。
- 范围：只改账本的**存放位置**、首次加载方式，以及面板上那句说明。折叠口径、增量同步、「只增不减」的保证一律不动。

### 实际改动

- `lib/ledger.js`：新增 `resolveDataRoot()` / `resolveLedgerPath()` —— Windows 依次取 `LOCALAPPDATA`、`APPDATA`、`%USERPROFILE%\AppData\Local`；macOS 取 `~/Library/Application Support`；其他系统取 `XDG_DATA_HOME`，缺省 `~/.local/share`。账本落在 `<数据目录>/dsh-usage/ledger.json`。
- 同一模块顺带修掉一个早在 1.5.0 就存在的落盘缺陷：`syncLedger()` 给消失的会话打 `goneAt` 时没有同时更新 `lastSeenAt`，而 `mergeLedgers()` 在同一 `offset` 的平局里只认 `lastSeenAt` 更新的那一行，于是磁盘上 `goneAt: null` 的旧行每次都赢回来——标记永远写不进盘，面板的「本机现存日志」把已删会话也算进去、「已删除 N 个会话」少报。修复：打标记时同步 `lastSeenAt`。
  `$DSH_USAGE_LEDGER` 仍以完整文件路径覆盖，`$DSH_HOME` 不再参与解析。
- 新增 `resolveLegacyLedgerPaths()` 与 `loadLedgerWithInheritance()`：首次加载时合并旧位置（`$DSH_HOME/usage-ledger/` 与 `~/.dsh/usage-ledger/`；`DSH_HOME` 指向别处时两处都看，去重后合并）；
  按会话取「读得更多」的一行、`createdAt` 取更早的；合并后写盘一次，**旧文件原样留在原处**，不移动、不删除。
- 新增 `imported.json` 导入记录（`resolveImportRecordPath()`）：每个旧文件记 `size` + `mtime` + 导入时刻，同一个版本只导入一次；旧文件被旧版 Harness 推进（大小或 mtime 变了）才会再次合并。
- `index.js`：首次加载改走 `loadLedgerWithInheritance()`；`scan` 里新增 `ledgerPath` 交给面板。没有保留 `config.ledgerPath`：账本位置不是配置项。
- `client.js`：概览条下账本说明行的浮层（`title`）改成「说明文案 + 账本文件路径」两行；文案写明账本在用户数据目录、卸载插件或重装 DSH 都不会删除它。
- `tools/seed-ledger.mjs`：用同一个缺省路径建账，同样继承旧账本；`--dry-run` 时 `write: false`，不导入也不写盘。
- `test/selfcheck.mjs`：新增存储位置与继承的断言（三个平台的缺省路径、`DSH_USAGE_LEDGER` 覆盖、`DSH_HOME` 不再影响落点、旧账本只导入一次、清零后旧历史不复活，以及模拟卸载插件 + 重装 DSH 后累计不变）。
- 文档与清单：`README.md` / `README.en.md` 的「累计用量与账本」整节重写（位置、继承、清零语义、卸载保证）；
  `docs/token-ledger.md` 增 §0.6 与 §3.1，§5 删掉 `ledgerPath` 配置项；`locale/zh.json` / `locale/en.json` 的简介同步；
  `package.json` 1.5.0 → **1.6.0**；`cordis.patch.yml` 注释改写。

### 遇到的问题及原因

1. **账本跟着 DSH home 走**：换 home（重装、换 profile 根目录）就等于换了一份账本，旧账本还在但没人读，面板上的累计看起来倒退。
   放到每用户数据目录，它才不随 Harness 的安装状态变化。
2. **「不丢」必须可核对**：只改路径而面板不提位置，用户无从判断该备份哪个文件。
   说明行的浮层于是带上账本路径（`scan.ledgerPath`），并写明卸载插件 / 重装 DSH 都不删它。
3. **老账本不能一搬了之**：1.5.0 的行记着每条会话读到第几条（`offset`）。若第一次同步前不先继承，新账本会把这些会话当新会话整份重读 ——
   轻则白扫几秒，重则当场重复计入。所以继承放在第一次同步之前，合并规则沿用「取读得更多的一行」。
4. **继承不能每次启动都做**：否则用户删账本清零后，旧历史会在下一次启动时从旧文件重新长回来。
   用 `imported.json` 记住「这个旧文件的这一版已经导过」（`size` + `mtime`）解决；旧文件被推进时指纹变化，自然再合并一次。
5. **旧文件一律不动**：本机可能仍装着旧版 Harness 在写那个文件，删或移都是越界操作。实现上只读不写。
6. **`goneAt` 写不进盘（1.5.0 遗留）**：独立验证时用「删掉会话 → 保存 → 重读文件」复现：内存里 `goneAt` 有值，落盘后变回 `null`，真实账本里也有 11 行这样的会话。
   根因是打标记不产生新事件、`lastSeenAt` 没动，而合并写按 `lastSeenAt` 决胜，磁盘旧行因此总能盖回内存里的标记。修复为打标记时一并更新 `lastSeenAt`，并补了落盘断言。

### 结果与验证

- **存储位置**：逐条核对三平台缺省值、Windows 的 `LOCALAPPDATA` → `APPDATA` → `AppData\Local` 回退顺序、
  `DSH_USAGE_LEDGER` 的覆盖优先级，以及 `DSH_HOME` 怎么改都不影响落点；旧位置候选在 `DSH_HOME` 指向别处时两处都在，
  且不会把新位置自己算成「旧账本」。
- **继承**：临时目录里放一份 1.5.0 旧账本，首次加载把它合并进新账本并写出 `imported.json`，旧文件内容与 mtime 未被改动；
  再次加载不再导入；改动旧文件后才会再合并一次；删掉新账本与 `.bak` 后旧历史没有复活，再删 `imported.json` 才重新导入一次。
- **卸载 / 重装**：把「插件目录 + DSH home」整个删掉再重新加载，旧行仍在；随后一轮同步把旧行标成 `gone`、
  把新 home 的新会话记进来，累计从旧值继续往上加（100 → 110），没有回退。
- 面板那行说明的浮层由 `client.js` 的 `ledgerCaption()` 拼成「说明 + 路径」两行（`scan.ledgerPath` 为空时只显示说明），
  文案中英同步。
- `node test/selfcheck.mjs` 全绿：新增存储位置、旧账本继承与「卸载 / 重装后累计不变」三组断言（旧的路径断言按新口径改写），
  原有「只增不减」契约一字未动。

### 遗留问题与风险

- `DSH_USAGE_LEDGER` 是唯一的覆盖方式；确实要以别处的账本为准得自己设它，profile 配置不再提供这个开关。
- 旧位置的账本只合并一次：若在 1.6.0 之后又把旧版 Harness 装回来继续使用，两份账本会各自前进，直到下一次 1.6.0 启动才再次合并；
  合并按会话取读得更多的一行，不会重复计入，但两份文件的起始时间可能相差几天。
- 账本在**每用户**数据目录里：换系统账号、或用户手动清理该目录，累计就没了 —— 这是「不随 DSH 卸载消失」的另一面。
- 卸载插件不会删除该目录；确实想彻底清掉时需要用户自己删 `dsh-usage` 目录（删 `ledger.json` 与 `.bak` 只是清零）。
